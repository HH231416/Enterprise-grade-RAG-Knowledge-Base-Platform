# 图增强检索（GraphRAG）第一版

校园综合知识库平台内的**公开制度与办事指南增强子系统**。围绕「事项—部门—材料—步骤—条款」的关联问答设计。

> **配套文档**：架构设计与模块职责见 [architecture.md](architecture.md)；>   
> 面试叙述与追问应答见 [interview.md](interview.md)。

> **基线来源**：业务基线取自优化版（约 2 万份原始文档、百万级知识片段、日均 300+ 查询）；
> 模型部署取自完整版的四卡 H20 目标方案；GraphRAG 为平台公开资料子系统的**增量设计**
> （只覆盖平台资料子集，不代表全部百万级分块都需构图）。

**当前状态：代码已完成第一版实现，已通过内存替身下的隔离测试。**

**尚未完成真实集成验证**：真实 Neo4j 的 Cypher 执行正确性、真实模型的抽取质量、真实 PostgreSQL 迁移、真实校园资料的检索效果均**未运行验证**。当前测试证明的是业务逻辑在 `InMemoryGraphStore` 下成立，**不等于** Neo4j 适配器、迁移结果与生产环境具有相同语义。

## 二、整体链路

```
前端问答（个人会话）
    ↓
QaService.conversation_answer
    ├─ 原有 Dense + BM25 + Rerank（权限按可信身份）
    └─ 按需图检索（仅公开资料）
              ↓
        GraphStore（Neo4j / 内存替身）
              ↓
        有效批次 + 来源快照校验
              ↓
        统一证据去重与排序
              ↓
        原文支持 / 适用条件 / 完整性检查
              ↓
        回答 · 澄清 · 有边界拒答
```

离线构图链路：

```
公开且可检索的文档
    ↓  start_batch（计算来源快照指纹，幂等）
创建构建批次
    ↓  run_extraction（LLM 受约束抽取 → 程序校验）
候选关系 + 校验结果落库
    ↓  管理员剔除错误候选 → approve_batch
批次已批准
    ↓  publish_batch（快照复核 → 写图 → 切生效指针）
批次 searchable，进入在线召回
```

## 三、图证据身份与发布版本

图证据身份 = **批次 + 来源文档 + 分块 + 关系**。四个问题分别由不同字段回答：

| 问题               | 字段依据                                                                                            |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| 该关系从哪个文档、哪个分块抽取？ | `graph_candidates.doc_uuid` / `chunk_uuid` / `chunk_index`                                      |
| 它对应哪一次文档内容和分块结果？ | `graph_build_batches.source_fingerprint`（覆盖 `file_hash`、`version`、`access_level`、审核与状态、逐分块内容哈希） |
| 哪个构建批次生成了它？      | `graph_build_batches.batch_uuid`                                                                |
| 管理员审核的是哪一批候选？    | `graph_candidates.batch_uuid` + `review_status`                                                 |
| 当前生效的是哪个已批准批次？   | `graph_active_batches` 指针（每文档唯一，且只指向 `status='searchable'`）                                     |
| 文档变化后旧批次为何不再使用？  | 指纹变化 → 旧批次置 `superseded`、指针撤销；在线召回只认生效指针                                                        |

**内容哈希的定位**：用于检测变化与辅助幂等（`uq_graph_batches_snapshot` 唯一约束），**不单独作为证据身份**。

**批次 ≠ 政策生效版本**。`source_fingerprint` 是技术构建单位；政策适用学年、人群、学历层次需在候选的 `applicability` 字段独立表达。

### 三种批次语义

| 情形                         | 行为                                                  |
| -------------------------- | --------------------------------------------------- |
| 同一来源快照重新构图                 | 命中幂等，复用原批次；即使重建也不动现有生效批次                            |
| 来源内容 / 分块 / 公开范围 / 可检索状态变化 | 旧批次 → `superseded`，指针撤销，立即阻断                        |
| 批准时来源已变化                   | 抛 `GraphSourceChangedError`，批次 → `failed`，要求重新构建与审核 |

## 四、批次审核闭环

| 阶段   | 状态               | 说明                   |
| ---- | ---------------- | -------------------- |
| 创建   | `pending`        | 仅公开且满足统一可检索条件的文档     |
| 抽取中  | `running`        | 逐分块调用抽取器             |
| 待审   | `pending_review` | 候选落库，**未批准前不参与在线检索** |
| 已批准  | `approved`       | 记录审核人与时间             |
| 已生效  | `searchable`     | 图写入成功且生效指针已切换        |
| 发布失败 | `publish_failed` | 可重试，不重复发布            |
| 已失效  | `superseded`     | 来源变化后不可用             |

**抽取结果分类**（五态，不允许把失败当空结果）：

| `extraction_result` | 含义                          |
| ------------------- | --------------------------- |
| `candidates`        | 成功抽取到候选                     |
| `empty`             | 成功执行但无可用候选                  |
| `llm_failed`        | 模型调用失败（超时/错误），**不静默切换规则抽取** |
| `invalid_output`    | 输出格式非法                      |
| `evidence_rejected` | 候选未通过证据校验                   |

**程序校验能证明什么**：受控类型白名单、关系方向、字段长度、两端实体一致性、原文锚点（`evidence_text` 必须逐字来自该分块、实体名必须在该分块出现）、适用条件未知保持未知。

**程序校验不能证明什么**：关系语义正确性。语义由人工批次审核负责。

**授权**：`/admin/graph/*` 全部挂 `require_admin_actor`，但该依赖在 `ADMIN_AUTH_ENABLED=false` 时返回 `None`。因此图审批与发布**额外要求非空管理员标识**，否则返回 403。资料公开不等于任何人都能发布图谱。

## 五、仅公开资料的约束

公开判定复用校园权限检查器的公开语义（`public` / `open` / `公开`），不另造一套矛盾字符串。检查点覆盖三处：

1. `start_batch` / `run_extraction` —— 创建与执行构建任务时
2. `approve_batch` / `publish_batch` —— 批准与发布时
3. `GraphRetrievalService._validate_relations` —— 在线召回、图扩展、证据进入回答前

资料从公开改为非公开、被撤回或删除时，`apply_document_eligibility` 立即阻断，**不等后台物理清理**。

一份来源失效只撤销该文档的指针与批次，**不删除其他有效来源支撑的实体与关系**。

## 六、检索与降级

| `graph_status` | 含义              | 行为                   |
| -------------- | --------------- | -------------------- |
| `disabled`     | 图功能未启用          | 纯文档检索，行为与改造前一致       |
| `empty`        | 已启用但无匹配关系或无实体锚点 | 纯文档检索                |
| `ok`           | 命中有效批次关系        | 合并进统一证据层             |
| `unavailable`  | 图存储不可用          | **降级**为纯文档检索，响应中如实标注 |

**不可降级的情况**：身份校验失败、权限拒绝、来源完整性失败 —— 直接抛出，不通过降级绕过。

### 关系类型大小写约定

业务边类型统一**大写**（`HANDLED_BY`），证据边 `relation_type` 属性保持受控枚举的**小写**  
（`handled_by`）。读取时用 `toLower(ev.relation_type) = toLower(type(r))` 归一化比较，  
`_row_to_relation` 把读回的类型归一化回小写。两侧不做归一化会恒不匹配，导致扩展查询返回空。

### 事务边界

批次替换通过 `session.execute_write()` 在**单个托管式事务**内完成「删除该批次证据边 + 写入全部新证据」。  
共用 session 多次 `session.run()` 不构成原子操作。

批次替换**只删除该批次的证据边，不清理共享实体节点**：同一业务关系可能由多个批次支撑，  
删除证据后端点仍被业务边连接，此时删除节点会违反 Neo4j 约束并误删其他来源的事实。  
孤立实体的清理由独立流程处理。

### 图模型：业务关系与来源证据分离

```
业务关系：(:GraphEntity)-[:HANDLED_BY]->(:GraphEntity)   共享的业务事实
来源证据：(:GraphEntity)-[:SOURCE_OF {batch_uuid, doc_uuid, chunk_uuid}]->(:GraphEntity)
```

同一业务关系可挂多条来源证据边。文档 A、B 都支持「事项 X 由部门 Y 受理」时，  
各自写入自己的证据边，互不覆盖；撤回 A 只删除 A 的证据边，B 的支持关系保留。

批次整体替换在**单个事务**内完成（先删该批次证据边再写入），  
不留下「已删未写」的中间态。

### 实体锚点如何确定（第一版）

图扩展需要实体锚点。第一版**不做问句→实体的字符串匹配**，而是复用既有 Dense 检索：

```
用户问句
  → 原有 Dense+BM25+Rerank 召回片段（doc_uuid 列表）
  → GraphAnchorResolver 从命中分块所属文档的已发布批次关系中收集实体键
  → 单跳邻接扩展（端点等值匹配）
  → 批次与来源快照校验 → 合并进统一证据层
```

理由：问句是自然语言（如「本科毕业申请需要哪些材料」），实体键是规范短名（如「本科生毕业学位申请」）。实测纯字符串方案无法同时避免误召回与漏召回——等值匹配完全召不回，单向子串漏长问句，字符二元组覆盖率会把「财务处」误判为命中「教务处」。因此把「问句→实体」的语义匹配交给已上线的向量检索，图检索只做「实体→关系」的图遍历。

**代价与边界**：图分支依赖文档检索先命中相应文档。若文档检索完全召回不到，图关系也召不回。这是第一版的已知限制，且不是静默失败——`graph_status` 返回 `empty` 并附 `message`。

**未采用的做法**：对问句做模糊/启发式实体匹配。未经真实数据验证的匹配规则不进入生产路径。

### 数据模型约束（ORM 与迁移逐项一致，共 5 处外键）

| 表.字段                              | 引用                               | 删除行为    |
| --------------------------------- | -------------------------------- | ------- |
| `graph_build_batches.doc_uuid`    | `documents.doc_uuid`             | CASCADE |
| `graph_candidates.batch_uuid`     | `graph_build_batches.batch_uuid` | —       |
| `graph_candidates.doc_uuid`       | `documents.doc_uuid`             | CASCADE |
| `graph_active_batches.doc_uuid`   | `documents.doc_uuid`             | CASCADE |
| `graph_active_batches.batch_uuid` | `graph_build_batches.batch_uuid` | —       |

三张新表的 `id` 均为 `BigInteger().with_variant(Integer, "sqlite")` 主键自增，  
与 `app/db/types.py` 的 `PrimaryKeyBigInt` 一致（SQLite 需 `INTEGER PRIMARY KEY` 才 ROWID 自增）。

### 证据合并规则

- 图关系不作为独立答案，必须回落到原文引用；关系路径作为**辅助解释**
- 去重按有效分块标识，**同一分块支持的不同关系全部保留**
- 保留多路命中信息（`recall_sources`）
- 图召回分**只作排序信号，不参与事实成立判断**
- 关系验证使用完整 `evidence_text`，**不用 240 字符展示摘要**
- 不把 Dense 与图检索的原始分相加

### 完整性检查

判定以**目标事项**为单位，该事项必须同时具备**全部**所需关系才算完整。

| 场景                       | 结果                  |
| ------------------------ | ------------------- |
| 问 A 的材料+部门，只有 A 的材料      | 不完整（缺 `handled_by`） |
| 问 A 的材料+部门，有 A 的材料、B 的部门 | 不完整（跨事项不能互相证明）      |
| 问 A，只有 B 的完整关系           | 无法确定所问事项 → 待澄清      |
| 问 A，A 的全部必要关系都有支持        | 完整                  |

无法从问题中确定所问事项时（问题未提及任何已召回事项名，或同时提及多个），  
返回 `subject_uncertain=True` 并列出 `candidate_subjects`，**不用任意召回事项代替用户所问事项**。

`GRAPH_REQUIRED_RELATIONS` 仅用于覆盖度自检，不参与单个问题的完整性判定。

第一版只对明确的关系类问题（`GRAPH_REQUIRED_RELATIONS` 列出的类型）检查必要证据：

- 缺任一必要关系 → `needs_clarification=true`，`answer_status=insufficient_evidence`，输出有边界说明，**不输出确定结论**
- 适用条件未知 → 提示以原文条款为准
- 高相似度或图上存在路径**不作为答案完整的证明**

## 十、演示案例（资料性质：虚构测试资料，非真实校园政策）

以下内容为**明确标记的虚构测试数据**，仅用于验证机制，不构成任何学校政策依据。

分块原文（虚构）：

> 本科生毕业学位申请由教务处受理。办理需要提交毕业申请表和学位申请表。申请流程包括在线申请、现场核验、领取证书。

抽取与审核后的候选：

| 关系                  | 源实体                  | 目标实体            | 原文证据             | 适用条件  |
| ------------------- | -------------------- | --------------- | ---------------- | ----- |
| `handled_by`        | 本科生毕业学位申请（procedure） | 教务处（department） | 本科生毕业学位申请由教务处受理。 | 原文未说明 |
| `requires_material` | 本科生毕业学位申请（procedure） | 毕业申请表（material） | 办理需要提交毕业申请表      | 原文未说明 |

用户提问「本科毕业申请需要哪些材料，由哪个部门受理？」时：

1. 文档检索命中该分块，向量召回结果提供实体锚点
2. 图检索从生效批次取回两条关系
3. 合并为同一分块上的两条 `graph_relations`，引用回落到原文
4. 完整性检查：`handled_by` 与 `requires_material` 均满足 → 正常回答

若只发布 `handled_by`（管理员剔除 `requires_material`），完整性检查判定证据不完整 → 输出「缺少：requires_material，不作确定结论」。

## 十一、尚未验证与待授权事项

### 已实现 + 已隔离测试（内存替身 + mock 模型，无真实服务）

- 会话归属隔离（创建/列表/读取/发送/删除、无主历史会话阻断、伪造 owner 无效）

- 存储接口契约：内存替身、Neo4j 适配器、不可用占位存储实现同等方法集
- 多来源关系隔离：同一业务关系来自不同批次时互不覆盖，撤回单源不影响他源

- 证据合并：第 0 块、UUID 类型差异、同分块多关系、未召回分块追加均正确
- 生成回答使用 `full_text` 完整原文，不用 240 字符展示摘要
- 历史上下文过滤：失效/失权/来源不明的历史知识不进入下一轮模型输入

测试数据库与存储目录使用会话级临时路径（`tempfile.gettempdir()/oa_rag_pytest/<run_id>`），  
每个测试会话独立，并在 teardown 中释放连接后清理。  
多测试文件可在同一进程内顺序运行，无需手工删除固定数据库文件。

### 不能声称的能力

- **Neo4j 适配器的 Cypher 未经真实数据库验证**
- 未做完整多跳推理或资格规则判断
- 未实现 DRIFT、社区发现、全校园自动建图
- 未构建学院/角色/个人资料的图权限体系
- 历史页面是否标注或隐藏失效来源的旧回答，仍待产品决策（模型输入已过滤，页面未改动）
- 图上存在路径不等于业务结论成立
- 完整性判断只覆盖第一版明确列出的五类问法，其余问法不做完整性判断
- 锚点依赖文档检索先命中相关分块，召不回则图关系也召不回

**建议**：先只读统计数量再决定。若历史会话仅是测试数据，选 (a) 即可。
