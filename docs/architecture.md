## 一、项目定位

平台主体是**校园综合知识库 RAG 平台**（检索与问答层，不替代交易系统）。
本文聚焦其中的**图增强子系统**：在 Dense + BM25 混合检索基础上，
对**公开校园制度与办事指南**引入**带原文溯源的图关系检索**，
改善跨文档关系问题的证据组织，并通过审核、版本管理与权限控制约束回答。

一句话定位：

> 大部分问题用文档检索回答；需要跨文档组织"事项—材料—部门—依据"关系时，
> 用图检索补充结构化证据，且图证据必须回落到原文，不允许脱离原文独立作答。

图子系统只覆盖平台资料的一个子集——**不代表全部百万级分块都必须构图**
（规模口径见 6.1，分层沿用见 8.1）。

## 二、为什么用图谱，为什么仍保留普通 RAG

### 2.1 图谱承担的部分

校园办事资料天然存在多类实体与关系：办事事项、所需材料、受理部门、办理步骤、依据条款。
这些关系**跨文档分布**——材料清单可能在一份指南里，受理部门在另一份制度附件里。

| 问题类型 | 例子 | 适合的检索方式 |
|---|---|---|
| 精确条款查询 | "补办校园卡需要工费 20 元吗" | 文档检索（关键词精确命中） |
| 自然语言描述 | "毕业答辩需要准备什么" | 文档检索（语义相似） |
| 关系组织 | "这个事项要交哪些材料、由哪个部门办、依据是什么" | 图检索（跨文档组织关系） |

### 2.2 不把所有知识都结构化的理由 `[设计决策]`

图谱的价值在于**关系**，不在于内容本身。把所有文本都塞进图谱会带来三个问题：
抽取成本高、召回粒度粗、原文溯源困难。

因此采用**混合策略**：
- 文档检索负责"找到说这句话的那一段"
- 图检索负责"把这段涉及的关系连起来看是否完整"

图关系**不作为独立答案**，必须回落到原文引用（`evidence.py` 的核心规则）。

## 三、模块职责与拆分理由

`app/graph/` 共 15 个模块，按职责分为五层 `[已实现]`：

### 3.1 类型与错误层

| 模块 | 职责 | 为什么独立 |
|---|---|---|
| `types.py` | 数据结构与受控枚举（关系类型白名单） | 关系类型必须受控，模型输出不能直接拼进查询；枚举集中定义便于审计 |
| `errors.py` | 区分**可降级故障**与**不可降级失败** | 存储故障可降级为纯文档检索；权限/完整性失败必须抛出，不能被降级掩盖 |

### 3.2 存储层

| 模块 | 职责 | 为什么独立 |
|---|---|---|
| `store.py` | `GraphStore` Protocol（接口契约） | 内存替身与 Neo4j 适配器必须能力对等，防止某一方缺方法导致静默返回空 |
| `neo4j_adapter.py` | 生产实现 | — |
| `memory_store.py` | 测试替身 + 本地演示 | 隔离测试不依赖真实服务 |
| `factory.py` | 按配置选实现 | **关键约束**：配置 neo4j 但不可用时返回 `UnavailableGraphStore` 而非内存——否则会产生"批次标记 searchable、进程重启后图数据消失"的假发布 |

### 3.3 构建与发布层（离线）

| 模块 | 职责 |
|---|---|
| `extractor.py` | LLM 受约束抽取：从分块文本抽取候选关系 |
| `validator.py` | 程序校验：结构合法性、原文锚点是否真实存在 |
| `builder.py` | 构图服务：批次生命周期（创建 → 抽取 → 校验） |
| `publish.py` | 受控发布：审核 → 写图 → 切生效指针 |

**为什么离线与在线分离** `[设计决策]`：
用户请求中不应该实时抽取整份文档。抽取是重操作（LLM 调用），
放构建期可以做、可以重试、可以审核；放在线会拖垮问答延迟。

### 3.4 检索层（在线）

| 模块 | 职责 |
|---|---|
| `anchors.py` | 实体锚点解析：复用向量召回结果确定实体 |
| `retrieval.py` | 有效批次校验 + 单跳扩展 |
| `evidence.py` | 图证据与文档证据合并 + 完整性检查 |

### 3.5 历史上下文层

| 模块 | 职责 |
|---|---|
| `history_filter.py` | 多轮对话中历史回答的证据有效性核对 |

## 四、三条核心流程

### 4.1 离线构建发布流程

```
文档上传
  → 解析、分块（DocumentChunk）
  → 创建构建批次（batch，快照指纹 = file_hash + 分块指纹 + 公开范围 + 可检索状态）
  → 逐分块调用 LLM 抽取候选关系
  → 程序校验（结构 + 原文锚点真实存在）
  → 候选进入 pending_review
  → 人工/规则审核（approved / rejected）
  → publish_batch：
       ① 校验来源快照未变化（变了则阻止发布）
       ② 在单个 Neo4j 事务内：删除该批次证据边 + 写入新证据边
       ③ 切换 graph_active_batches 生效指针
  → 批次 searchable，开始参与在线检索
```

**关键设计** `[已实现]`：

1. **发布顺序是"校验快照 → 写图 → 切指针"**。未被指针选中的批次即使写入图也不影响在线回答。
2. **来源快照变化阻止发布**。文档在抽取后被修改，快照指纹变化，批次拒绝发布。
3. **批次整体替换用单事务**（`session.execute_write`），避免"旧证据已删、新证据未写"的中间态。
4. **只删该批次证据边，不删共享端点**。同一业务关系可能由多个批次支撑，删除节点会违反 Neo4j 约束并误删他源事实。

### 4.2 在线问答流程

```
用户提问
  → 身份校验 + 权限校验（不可降级，失败直接抛出）
  → Dense 向量召回 + BM25 稀疏召回 + 融合 + rerank
  → 得到 top-k 文档分块（含 chunk_index）
  → 【图增强分支】
       ├─ 锚点解析：从命中分块所属文档的已发布关系收集实体
       │    └─ 状态区分：ok / empty / unavailable
       ├─ 单跳邻接扩展（graph_expand_limit 限制，默认 50）
       ├─ 批次有效性与来源快照校验
       └─ 图证据合并进统一引用列表
  → 完整性检查（关系类问题）
  → LLM 生成（使用分块完整原文，非展示摘要）
  → 响应含 graph_status / completeness
```

**降级行为表** `[已实现]`：

| 状态 | 含义 | 行为 |
|---|---|---|
| `disabled` | 图功能未启用 | 纯文档检索 |
| `empty` | 可用但确实没有可用关系 | 纯文档检索 |
| `unavailable` | 图存储不可用或读取失败 | **降级**为纯文档检索，响应中如实标注 |
| `ok` | 命中有效批次关系 | 合并进统一证据层 |

**不可降级**：身份校验失败、权限拒绝、来源完整性失败 —— 直接抛出，不通过降级绕过。

### 4.3 文档更新与失效流程

```
文档内容变更 / 撤回 / 删除 / 权限变更
  → 来源快照指纹变化
  → 【路径 A】该文档已有生效批次：
       校验失败 → 阻止继续作为权威证据
       检索层快照比对不通过 → 该文档关系不再进入回答
  → 【路径 B】单源失效（该文档是唯一来源）：
       只撤销该文档的生效指针
       不误删其他文档支撑的同一业务关系（证据边独立）
  → 历史回答中的引用：
       构造下一轮模型上下文时核对来源
       已失效 / 失权 / 分块已删 / 版本已变 / 来源不可确认
       → 不作为可用知识传给模型
       → 但数据库原始记录保持不变
```

**为什么历史回答要单独处理** `[设计决策]`：
当前检索正确，不代表历史回答仍然适用。多轮对话如果无限复用旧答案，
会出现"制度已改但模型仍按旧条款回答"。过滤发生在**模型输入层**，
不修改用户已保存的内容——这两件事是分开的。

## 五、边界与已知局限（面试须主动说明）

### 5.1 图检索依赖文档检索提供锚点

**现状** `[已实现]`：先召回文档分块 → 从命中分块所属关系收集实体 → 单跳扩展。

**为什么这样设计**：复用已上线的 Dense 检索能力承担"问句→实体"的语义匹配，
图检索只做"实体→关系"的图遍历。不引入额外的实体识别模型，控制实现复杂度。

**局限**：原有检索完全漏掉相关资料时，图分支未必能补救。

**为什么不自己匹配问句** `[已验证的取舍]`：实测三种字符串方案都不可用——
等值匹配对长问句永不命中；单向子串漏召回；字符二元组覆盖率会把"财务处"
误判为命中"教务处"。未经真实数据验证的启发式不进入生产路径。

**演进方向**：别名归一化表、结合会话上下文解析目标事项。

### 5.2 事项识别采用保守字面匹配

**现状** `[已实现]`：`_resolve_target_subject()` 在问题文本中做归一化子串匹配，
命中唯一事项才确定目标事项。

**局限**：别名、省略主语、复杂多轮指代会触发澄清而非直接回答。
这是**有意的保守选择**——宁可澄清，不用错误事项作答。

**演进方向**：别名归一化、指代消解、结合会话历史的主体继承。

### 5.3 完整性检查是对已建模关系的检查

**现状** `[已实现]`：目标事项必须**同时具备全部**所需关系才算完整。
无法确定目标事项时返回待澄清，不猜测。

| 场景 | 结果 |
|---|---|
| 问 A 的材料+部门，只有 A 的材料 | 不完整（缺部门关系） |
| 问 A 的材料+部门，有 A 的材料、B 的部门 | 不完整（跨事项不能互相证明） |
| 问 A，只有 B 的完整关系 | 无法确定所问事项 → 待澄清 |
| 问 A，A 的全部必要关系都有支持 | 完整 |

**必须说清的边界**：
"部门和材料关系均存在"只证明**满足当前定义的关系要求**，
不证明材料清单覆盖了所有例外条件，**更不等同于资格规则推理**。
图中存在路径不等于业务结论成立。

### 5.4 关系抽取依赖 LLM

**现状**：受约束抽取（枚举白名单 + 结构化输出 + 原文锚点要求），
但语义正确性无法由程序完全保证。

**为什么仍需人工审核**：程序能检查结构合法性和原文锚点真实存在，
不能充分保证"这个关系抽对了"。公开制度更新相对可控，采用批次审核具有业务合理性。

## 六、性能与容量设计

> **重要**：本节全部内容为 `[假设]` 下的容量设计推演，**不是实测指标**。
> 真实性能需要压测验证，当前未执行 `[未验证]`。

### 6.1 规模口径：平台业务基线 + 图子系统设计假设

> **业务基线**（取自`简历项目_4天面试学习计划（优化版）`）：平台为校园综合知识库，
> 覆盖校内 **6 个业务单位**，约 **2 万份**原始文档（教务处制度约 3000、各学院制度约 5000、
> 课程大纲约 8000、课题组资料约 4000），切分后约 **百万级知识片段**（实际约 110 万），
> 日均 **300+ 次**学生查询（单日峰值 500+）。总体规模以优化版为准，
> 不再采用其他文档中"十万级原始文档"的旧口径。
>
> **模型部署**：取自完整版的**四卡 H20 目标方案**（见 8.6）。
>
> **图子系统**：只覆盖平台资料中的**公开校园制度与办事指南子集**，不代表全部
> 百万级分块都需构图；其文档量、实体数与关系数无明确来源，**保留为设计假设**，
> 不转写为已确认的业务数据。

| 层次 | 项 | 数值 | 性质 |
|---|---|---|---|
| 平台业务 | 原始文档 | 约 2 万份 | 优化版简历口径 |
| 平台业务 | 知识片段 | 约百万级（约 110 万） | 优化版简历口径 |
| 平台业务 | 日均查询 | 300+（单日峰值 500+） | 优化版简历口径 |
| 图子系统 | 构图文档范围 | 公开制度与办事指南子集 | `[设计假设]` 无明确来源，待真实构图统计回填 |
| 图子系统 | 分块 / 实体 / 关系规模 | 待定 | `[设计假设]` 同上 |

> 峰值不以日均推算；容量结论以压测为准，本文不另设容量假设。

### 6.2 延迟预算口径

**既有文档检索链路**：沿用 **P95 < 200 ms 的设计目标**。统计范围为
`Query Embedding → Dense 向量检索 → BM25 稀疏检索 → RRF 融合 → Rerank 精排`，
**不含回答生成**（生成独立统计）。

**图增强路径**在检索链路之外额外经过：

```
锚点读取 → 图关系扩展 → 批次及来源校验 → 证据合并
```

原有文档检索与图增强路径**分别安排延迟预算**。四卡 H20 部署为模型服务提供资源基础；
图分支复用查询结果、不新增在线关系抽取调用，通过受限扩展（单跳、`graph_expand_limit`）
与候选控制约束增量开销。总体延迟目标仍需结合模型输入、候选数量、并发及图查询方式判断，
**当前不作为实测结果**。

> 以下分阶段数字仅用于说明各环节的量级归属，均为 `[假设]` 估算，不构成任何预算结论。

| 阶段 | 估算量级 | 说明 |
|---|---|---|
| 向量化（单块，离线） | 10 ~ 50 ms | 取决于 embedding 服务；批量入库时并行摊薄 |
| BM25 稀疏召回 | 1 ~ 5 ms | Milvus 稀疏字段 |
| 稠密向量检索 | 5 ~ 20 ms | 取决于索引规模与硬件 |
| 融合 + rerank | 50 ~ 200 ms | rerank 是既有链路主要开销 |
| 图锚点读取 | 10 ~ 50 ms | 一次按分块读 + 内存过滤 |
| 图单跳扩展 | 5 ~ 30 ms | 限深 1 跳，`graph_expand_limit=50` |
| 批次与来源校验 | 1 ~ 10 ms | 少量 SQL |
| LLM 生成 | 1 ~ 5 s | 与检索分开计量，单独统计 |

### 6.3 设计中的性能保护措施 `[已实现]`

| 措施 | 作用 |
|---|---|
| 构图与问答分离 | 用户请求中不做 LLM 抽取 |
| 锚点复用召回结果 | 不新增查询向量化与在线模型调用；图查询与校验开销为实际增量（见 6.2） |
| `graph_expand_limit=50` | 限制单次扩展返回关系数，避免无界遍历 |
| 单跳扩展 | 不做多跳，避免查询爆炸 |
| 分块锚点收敛 | 只读命中分块上的关系，不读整篇文档的全部关系 |
| 按批次分区存储 | 替换/撤销只影响单个批次 |
| 存储故障降级 | 图不可用时问答仍可用 |
| 检索层连接池 | `db_max_overflow=20` |

### 6.4 扩容方式 `[设计方案]`

| 组件 | 能否独立扩展 | 说明 |
|---|---|---|
| 文档检索（向量/稀疏） | 可 | 索引可分片；稀疏索引可换 ES |
| rerank 服务 | 可 | 独立部署，横向扩容 |
| Neo4j | 可 | 只增不减的关系型负载，读扩展优于写 |
| LLM 生成 | 可 | 独立服务，按并发扩容 |
| PostgreSQL | 部分 | 元数据与分块；分块表增长后可分区 |

### 6.5 更新成本

| 操作 | 成本 | 说明 |
|---|---|---|
| 单文档内容变更 | 局部重建 | 只重建该文档的批次，`replace_batch` 只替换该批次证据边 |
| 单文档撤回 | 指针撤销 | 只撤该文档生效指针，不误删他源支撑的关系 |
| 新增文档 | 增量 | 新建批次，不影响既有批次 |
| 权限变更 | 无需重建 | 权限在检索层判定，不进图 |

### 6.6 图数据质量 `[未验证]`

当前图数据质量**未做全面评估**。需要评估的维度：
抽取准确率（关系是否抽对）、实体归一化效果（同一实体是否被当作两个）、
关系覆盖率（有多少事项具备完整关系）。

这些指标需要真实资料 + 人工标注才能得出，当前**不给出任何数字**。

## 七、已实现能力与未验证清单

### 8.3 两条路线的架构取舍（核心）

校园图检索的入口存在两条可行路线。参考项目走的是路线 B，校园第一版选择路线 A：

| 维度 | 路线 A：文档召回 → 实体锚点 → 图扩展（第一版采用 `[已实现]`） | 路线 B：文档检索 + 独立实体/关系检索 → 融合（参考项目走法，演进方向 `[设计方案]`） |
|---|---|---|
| 主要收益 | 复用原有检索，结构简单，新增模型调用少 | 图分支提供独立候选来源：文档漏召回时可补救；文档**部分命中**时也可能补充缺失关系、改善排序与证据覆盖 |
| 主要代价 | 文档漏召回时，图分支失去入口；文档部分命中时的补全能力弱于独立图检索 | 图对象向量化、索引随批次维护、融合设计复杂度 |
| 新增在线调用 | 不新增查询向量化或在线关系抽取调用；仍增加图查询及有效性校验 | +1~2 次 Neo4j 向量检索 + 融合计算 |
| 新增离线成本 | 不新增实体/关系向量索引维护；仍有关系抽取、审核、图写入与批次更新成本 | 实体/关系向量随批次发布同步写入 |
| 所需向量索引 | 仅分块（已有） | 实体（必须）+ 关系（可选） |
| 检索链路延迟 | 图分支复用查询结果、不新增在线关系抽取调用；其增量（锚点读取→扩展→校验→合并）与文档检索**分别安排预算**，不并入同一结论 | 需重新评估（含多路并发与融合重排） |
| 失败模式 | `graph_status=empty`，不静默 | 引入融合权重调参空间，无评测数据时难以校准 |

**第一版选择路线 A 的理由**（充分理由共三条，不依赖否定路线 B）：

1. **复用已有基础能力**：文档检索入口已上线并验证，"问句→实体"的语义匹配
   交由既有向量检索承担，不新增实体识别或独立实体向量索引的模型与维护成本。
2. **先建立关系、审核与溯源闭环**：第一版目标是在有限的校园公开办事事项上，
   把"抽取→校验→审核→发布→检索→回落原文"的闭环做完整、语义清晰；
   独立图检索通道会同时放大闭环内任何质量问题。
3. **改造范围可控**：图分支作为增强挂在现有检索之后，失败模式（`graph_status`）
   明确可控；为独立实体检索保留了接口升级空间（见 8.4）。

**路线 B 的潜在增益如实记录**：文档漏召回时的独立补救、部分命中时的关系补全与
排序改善。第一版优先控制复杂度，不因路线 B 有增益就预先引入；何时升级由
需求形态与成本收益判断（见 8.4）。

**路线 A 的已知局限**（继承 5.1）：文档检索完全漏召回时，图分支无法补救；
文档部分命中时，补全能力也受限于已召回分块上的关系——
这两类场景正是升级到路线 B 要解决的问题。

### 8.4 升级到路线 B 的考量 `[设计方案]`

升级由**需求形态与成本收益**驱动，不设数字门槛，也不以完整评测集为前置条件：

- **需求信号**：实际使用中频繁出现别名表达（问句不含规范事项名）、
  跨文档证据缺失（文档部分命中但关系不全）、基础召回不足（文档检索漏召回）。
- **成本收益判断**：维护实体向量索引（构图、随批次重建、融合调参）的
  收益是否值得其成本，结合当时的维护能力评估。
- **决策辅助**（可选，非门槛）：代表性问题案例分析或小规模对照验证
  （例如在候选问题集上对比文档检索与独立实体检索的召回差异）。
  评测是**辅助决策的方法**，不是设计推进的硬门槛。
- **注意**：只运行路线 A 无法直接测得"独立图检索能补救多少"——
  该数字需候选方案或人工分析才能估计，不作为在线统计指标。

**升级路径**（分两步，借鉴参考实现）：

1. **第一步（Local 等价物）**：建立实体向量索引，与文档检索 RRF 融合，
   引入 `matched_by` 多路命中标记；一次 query embedding 供两路复用。
   前提：文档索引与实体索引采用**兼容的嵌入模型与向量空间**，
   不能仅因维度相同就共享向量。
2. **第二步（Triplet 等价物）**：关系文本向量化。受控枚举类型名本身区分度低，
   但向量检索可编码"事项＋关系＋对象＋描述"整条三元组文本，
   是否有区分度增益由届时评测判断。
3. **保持不变**：图证据回落原文、完整性按事项判定、批次审核闭环——
   这些是业务约束，不随检索路线改变。

| H20 卡 1、卡 2 | 在线问答生成，**双副本 + 负载均衡**，分别承载一个生成副本 | Qwen3-32B，FP8（每副本单卡） |
| H20 卡 3 | 在线检索：Embedding 与 Rerank 作为独立服务 | Qwen3-Embedding-8B（4096 维）+ Qwen3-Reranker-8B，FP8 |
| H20 卡 4 | 离线复杂图表理解 | Qwen3-VL-32B-Instruct，FP8 |
| CPU 节点 | 文字、表格解析 | PaddleOCR |

**必须说清的边界**：

1. **目标设计 ≠ 已上线**。上表是选定的部署设计，本文档采用它不代表已实测部署。
2. **双副本 ≠ 双卡张量并行**。两个单卡副本 + 负载均衡是 HA 方案（单卡故障可切换）；
   单套双卡张量并行是另一种方案——两者不混写。
3. **业务后端通过内网接口访问模型服务**，不在 API 进程内加载模型权重。
4. **Embedding 与 Rerank 共卡需考虑资源配额与并发竞争**，不宣称彼此完全隔离。
5. **图关系抽取复用生成模型服务**：安排在后台并限制并发、优先低峰运行——
   这是**设计安排**，不默认声称调度机制已实现。

**对图子系统的含义**：图分支不新增在线模型调用（锚点复用召回结果）；
构图期的关系抽取复用生成服务，属于离线任务，与本系统"构图与问答分离"的
既有设计一致（见 3.3）。
