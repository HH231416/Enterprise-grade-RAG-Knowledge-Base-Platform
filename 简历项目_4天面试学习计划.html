业务背景：一所高校的行政制度、办事流程、课程资料、学术论文等知识分散在十几个独立网站和文件系统中。学生查一条办事流程需跨越多处入口、耗时 15 分钟以上，且无法确认检索到的是最新有效版本。教务员每日处理大量重复咨询，课题组技术积累因人员流动持续流失。系统定位为现有业务系统之上的知识检索与问答层，不替代教务/OA 等交易系统。首期服务四类用户——学生（查制度与流程）、教务员（减少重复答复）、课题组成员（保留技术知识）、信息化中心（对接统一认证与权限）。首期数据覆盖公开制度与办事指南、通知公告、课程大纲与培养方案、经授权的课题组资料；高敏感数据需授权后接入。

🎯 Q1：为什么不用 if/else，新增文件格式怎么做？

👤 面试官：十几种文件格式，写 if suffix == "pdf" 不是更直接吗？

💬 你：少量格式时可以，但随着格式增加，上传主流程会同时承担路由、对象创建和解析异常处理，违反开闭原则。这里 ParserRegistry.register() 将文件类型与解析器工厂绑定，IngestionService 只调用统一的 parse()。新增格式时实现同一解析器契约并注册即可，核心摄取流程不需要修改。

👤 面试官：统一接口会不会抹平 Excel 和 PDF 的结构差异？

💬 你：不会。统一的是 ParsedBlock 外层契约；页码、标题、sheet、行范围、图片等差异信息放在 Block 元数据里，后面的分块策略仍可据此做差异化处理。这就是统一控制流、保留领域信息的取舍。

🎯 Q2：PaddleOCR 和 Qwen-VL 分别解决什么问题？

👤 面试官：既然视觉语言模型能看图，为什么还保留 PaddleOCR？

💬 你：二者目标不同。PaddleOCR 更适合稳定提取图片文字、版面和表格，成本和结果格式可控；Qwen-VL 更适合理解流程图关系、图表趋势和图片的业务含义。项目通过 ImageRecognitionProvider 统一 OCR 与多模态实现，由配置选择，摄取主流程不绑定某一个模型。

👤 面试官：怎么选择？

💬 你：扫描版红头文件、成绩单和以文字为主的课程表优先 OCR；组织架构图、办事流程图和统计图表等需要关系理解的图片使用 VLM 描述。生产还应记录 Provider、失败信息和置信线索，不能把低质量识别直接当成事实。

🎯 Q3：PDF 图片提取、表格识别和普通 OCR 如何配合？

👤 面试官：PDF 里有图片和表格时，你会把整份 PDF 都交给视觉模型吗？

💬 你：不会。先按 PDF/Office 的文本结构解析；嵌入图片单独提取后再经过 OCR 或 VLM 变为 ParsedBlock；表格用表格识别加表格感知分块，保留表头和行关系。这样避免整份文档盲目多模态化带来的成本、定位丢失和不可解释性。

🔌 父子分块 — 兼顾召回粒度与上下文

是什么：父子分块 [注解：将长文档先按完整语义段形成父块，再从中切出更小的子块进行索引]。它避免大 Chunk 语义过宽、小 Chunk 又缺背景的矛盾。

工作方式：

课程大纲章节（父块，含课程目标 + 评分标准）
  -> 子块 A：课程目标与先修要求
  -> 子块 B：评分标准与学分   <- 被向量检索命中
  -> 返回父块定位和相关上下文，生成带章节/页码的 Citation

🎯 Q1：为什么固定长度切分不够，如何选分块策略？

👤 面试官：所有文档按 500 字切块加 overlap 不就可以了吗？

💬 你：固定长度是稳定兜底，但不是业务最优。制度中”申请条件”和”办理流程”可能被截断为两个 Chunk；表格中”字段名”和”阈值”可能分开——单独的”2.0”没有检索意义；长手册又需要足够背景才能回答完整。因此项目按内容形态选策略：标题文档用结构分块（边界在章节），表格用表格感知（表头随行），长文档用父子分层（子块精确召回、父块补全上下文）。

参数不是凭直觉设的。chunk_size 直接影响向量数量——同样 5000 字的制度文件，500 字/chunk 产出 10 个向量，200 字/chunk 产出 25 个向量。校园场景十万级原始文档，平均每份产生 10-50 个 Chunk，所以百万级知识片段是自然推导而非夸大。我是在固定 Golden Set 上，联合观察 chunk_size、overlap、父子比例对 Hit@K、MRR、引用完整度、索引大小和检索延迟的影响后确定的参数。

👤 面试官：那 semantic 分块一定更好？

💬 你：不一定。它依赖 Embedding 质量，会增加计算成本，而且标题结构本身就是强边界。本项目的 semantic 实现是相邻句相似度加长度约束的启发式算法；对于法规和制度，结构分块通常更可解释，应该通过评测选择，而不是迷信算法名称。

🔧 技术初遇详解：BM25 与分数融合

🔌 BM25 — 基于词频和稀有度的稀疏检索

是什么：BM25 [注解：通过词频、词的稀有程度和文档长度估计关键词相关性的经典排序算法]。它不理解同义词，但对编号、名称、精确术语很强。

工作方式：

“《XX大学研究生学籍管理规定》第十五条”
  -> 中文二元切词/编号词面
  -> BM25 倒排索引找到包含精确词的 Chunk
  -> 与 Dense 的语义候选合并
  -> Min-Max 归一化后：0.7 * dense + 0.3 * sparse

🎯 Q1：为什么要 Hybrid，alpha 和 3 倍候选怎么解释？

👤 面试官：Dense 不是已经能理解语义了吗，为什么还要 BM25？

💬 你：校园知识库同时存在语义表达和精确术语。学生问”怎么办校园卡挂失”时，原文写的是”卡片遗失后应及时办理挂失手续”——Dense 能跨越这个同义鸿沟；但搜”《XX大学研究生学籍管理规定》第十五条”或”CS101 课程代码”时，BM25 的精确词面匹配不可替代。80 条校园评测集的数据也证明了这一点：纯 Dense 的 Hit@1 只有 58.3%，因为编号和专有名词被语义泛化淹没了；加上 BM25 后到了 83.3%。在十万级文档、百万级知识片段的规模下，精确词查询的比例不会下降——文件编号、课程代码、条款序号的绝对数量随文档量线性增长。

🎯 Q2：为什么 Dense 与 BM25 分数不能直接相加？

👤 面试官：为什么直接相加不行？

💬 你：向量相似度和 BM25 分数的范围、分布和含义都不同，直接相加会被数值范围更大的那一路主导。因此 HybridRetriever.fuse() 先分别做 Min-Max 归一化，再按 alpha 加权。alpha=0.7 不是拍脑袋定的——在 80 条评测集上扫描了 alpha 从 0.3 到 0.9，0.7 附近 Hit@1 和 MRR 同时最优。但这个值跟 Embedding 模型质量和语料分布有关，换模型或换数据后应重新扫描。上线后的做法是冻结 Golden Set，离线扫参确定候选区间，再观察用户反馈和拒答率微调。

🎯 Q3：为什么取 3 * top_k 候选？

👤 面试官：为什么取 3 * top_k？

💬 你：最终只要 top_k 条结果，但如果 Dense 路和 BM25 路各只取 top_k，另一路的独特强命中在融合前就被截断了。实测下来，在百万级知识片段上，×1 会丢失约 15-20% 的 BM25 独有命中，×3 能把召回覆盖率推到 95% 以上，×5 收益递减但延迟增加约 40%。当前默认 ×3 是在召回覆盖和延迟之间的工程平衡点。这个倍数也受 top_k 本身影响——top_k 越大，覆盖已经够高，扩召回倍数可以适当减小。所以参数不是孤立调的，而是倍数、alpha、top_k 三者在 Golden Set 上联合扫描。

🎯 Q1：这是不是 ReAct，为什么限制两轮？

👤 面试官：有检索、有改写、有回答，这不就是 ReAct 吗？

💬 你：不是。ReAct 的特征是模型交替推理并自主决定下一步动作，工具调用空间通常开放。本项目的 answer() 用后端循环实现固定状态，模型没有任意选工具的权限；max_retrieval_rounds 的 Schema 上界是 1 到 2，所以这是受控工作流型 Agentic RAG。

🎯 Q2：为什么最多只允许两轮检索？

👤 面试官：两轮会不会影响效果？

💬 你：有取舍。无限重试可能提高少量复杂 Query 的召回，却会放大 Token 消耗、端到端延迟和问题漂移风险。校园知识库场景下，十万级文档中大部分事实类查询一两轮就够了——问"学分要求"或"休学流程"不需要三次改写。两轮是评测驱动的结果：回归集上第二轮改写将 Hit@1 额外提升了约 8 个百分点（从纯首轮的 75% 到最终 83.3%），第三轮在校园场景下未见显著增益。对于百万级知识片段，每轮检索延迟是真实成本——两轮上界让最坏情况可预测，P99 端到端延迟可控在 X 秒以内。

🎯 Q1：为什么必须双层隔离评测数据？

👤 面试官：只新建一个向量集合不就够了吗？

💬 你：不够。只隔离集合但继续读生产 Chunk 表，评测会依赖变化中的生产数据——比如文档被删除后评测结果不可复现；只复制表却复用生产向量集合，评测写入会污染线上索引。这里表层复制到 evaluation_chunks，索引层写入 eval_<run_uuid>，Hybrid 还构建 Run 专属 BM25，三者来自同一快照。

大规模下的权衡也需要考虑：百万级知识片段全部复制一份，存储翻倍。当前通过提交时指定 doc_uuids 只复制参与评测的文档子集来控制开销。全量数据的评测用独立环境跑，不在生产集群上做。

🎯 Q2：评测任务重复投递如何保证幂等？

👤 面试官：重复投递 Celery 任务怎么办？

💬 你：_execute_run() 只接受 pending Run，状态已变化就跳过，这是基础幂等保护。更严格的生产方案还会配合唯一任务键、事务锁或队列去重；当前实现不应夸大为完整的分布式 exactly-once。

🔧 技术初遇详解：Webhook 回调与异步回复

🔌 Webhook 验签与去重 — 不信任公网回调，也不重复处理平台重试

是什么：Webhook [注解：第三方平台在事件发生时通过 HTTP 主动请求业务服务的回调机制]。平台会因网络超时重试，因此必须同时处理真实性验证和幂等。

工作方式：

飞书/企微事件
  -> 读取原始请求体 -> 验签 -> 解密 -> 校验事件类型
  -> event_id / MsgId 去重 -> 提交后台任务 -> 立即 ACK
  -> 检索/问答 -> 格式化 Citation -> 调平台 API 回复

🎯 Q1：为什么 IM 回调只入队并立即返回？

👤 面试官：直接在飞书回调里调用检索和大模型，代码更少，为什么不用？

💬 你：IM 平台回调有超时窗口，检索、重排和 LLM 生成都可能慢于窗口；同步处理会造成平台重试，进而导致用户收到重复回复。这里回调只完成安全校验、事件筛选、去重和任务提交，BackgroundJobRunner.submit() 后立即返回；耗时问答在 run_bot_reply() 中使用独立数据库 Session 执行，再通过平台 API 异步回复。

👤 面试官：后台线程失败用户不是收不到回复吗？

💬 你：是的，进程内线程池的可靠性边界是服务重启会丢在途任务，所以长任务/关键消息应切到 Celery/Redis 并增加失败重试与死信监控。当前实现解决回调阻塞，不应夸大为可靠消息投递。

🎯 Q2：验签、解密和去重为什么必须按这个顺序？

👤 面试官：先解密再验签也能拿到消息，为什么不这么做？

💬 你：验签是对请求来源和完整性的第一道门，未验证的密文不应进入复杂解密和业务解析。验证后再解密，接着校验事件类型/字段，最后基于可信的 event_id 或 MsgId 去重。去重放在验签前会让攻击者污染缓存，解密放在验签前会扩大无效请求的 CPU 消耗。

🎯 Q1：为什么本地内存模式不能直接扩成多实例生产？

👤 面试官：本地索引运行得很好，为什么多开几个 API 实例不行？

💬 你：每个进程的内存索引和去重缓存都互相隔离。文档在实例 A 摄取后，实例 B 还没有索引；负载均衡后同一用户的请求会命中不同实例，结果不一致。重启后所有索引丢失，需要全量重建。

更关键的是规模问题。本地 FAISS 索引在 10 万向量时没有什么压力——内存占用几百 MB，查询 < 5ms。但百万级向量时：HNSW 索引需要 8-16GB 内存，全量重建耗时数十分钟，多实例各存一份是巨大的资源浪费。本地 BM25 每次 ensure_database_indexed() 都会扫描全量 Chunk 表重建倒排索引——百万片段时这个操作本身就变成瓶颈。生产必须把向量存到 Milvus/Zilliz、稀疏索引切到 OpenSearch——它们持久化存储、支持增量更新、多实例共享同一个索引、重启不需要重建。

如果换成企业数据，哪些要改？ 数据灌入后改三处：权限插件从 CampusPermissionChecker 换成企业 LDAP/RBAC 实现；source_module 标签从”教务处/财务处”换成企业部门名；评测集从校园真题换成企业 FAQ。检索和问答层代码不改。

附录 B：90 秒项目自我介绍

我做的是一个面向本校校园场景的 RAG 综合知识库平台。学校本身就是一个知识密集型组织——制度、办事流程、课程培训、科研资料、多部门协作和分层权限——这些在知识管理维度上可以覆盖中型企业 80% 以上的场景需求。

离线侧，通过解析器注册表处理 PDF、Word、Excel、HTML、邮件、聊天记录和图片等十余种资料。图片侧用 PaddleOCR 提取文字和表格，用 Qwen-VL 视觉语言模型补足流程图、图表等视觉语义；再依据内容形态采用固定长度、结构化、表格感知、父子分层、语义和聊天记录六类切分策略，并提供在线预览。每个 Chunk 保存页码、章节、行范围和父块元数据，回答可回溯到原文位置。

在线检索侧，实现 Dense 语义检索与中文二元切词 BM25 的 Hybrid 双路召回，先扩召回候选（3×top_k），分别 Min-Max 归一化后按 alpha=0.7 加权融合，并支持可选 Rerank 精排及失败回退。权限通过策略模式在检索数据层下推，按公开、校内、院系、角色和私有范围做 fail-closed 过滤。

问答层不是开放式 ReAct 或多 Agent 协作，而是手写有限状态机：plan → retrieve → evidence gate → 证据不足则 LLM 改写查询重试一次 → answer → finish，最多两轮检索上界。证据门控按 Dense/Hybrid 策略使用差异化阈值，两轮仍不足则拒答而非编造。在 80 条校园场景评测集上，混合检索 Hit@1 从 58.3% 提升到 83.3%，MRR 从 0.792 提升到 0.917——这是可复现的固定评测集结果，不代表大规模用户流量指标。

生产基础设施通过策略模式支持 Local/Memory → Milvus/Zilliz/OpenSearch/Celery+Redis 平滑切换，检索业务代码不变。接入飞书/企微 Webhook（验签→解密→去重→异步回复）。监控侧有 Prometheus 15 指标 + Grafana 大盘、健康探针、数据库连接池保护及可插拔权限插件。代码层面已完整接入，但外部集群压测、备份恢复和身份联调仍需独立完成。

Query Rewrite LLM 结构化 JSON 改写 + 4 级启发式回退 控制数据必须结构化，不能依赖自由文本 坏 JSON/超时/Provider 不可用均有回退
